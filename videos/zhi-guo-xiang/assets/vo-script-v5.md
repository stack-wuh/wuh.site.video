## 三 · 为什么上一版"机械"——配音师给的实测根因

> **一处更正，留痕**：配音师第一轮报的是"语速快 40%"，**那是错的**——他把"规划 cps（分母含气口）"和"实测 cps（分母不含气口）"直接比了。同口径重算只快 **18%**。任何"全片统一降速 −40%"的方案都作废。下面是更正后的版本。

| # | 病因 | 数据 |
|---|---|---|
| ① | **逐行语速没有标定**（最主要） | 剧本每行的"每字占用总时长"自身差 **46%**（0.288 s/字 ~ 0.422 s/字）。一条统一 rate 必然让一半的行不落位——同一档 −18%，S10 会超 0.79s，her-06 会短 0.96s。**短句被念短、长句被念长 → 时快时慢 → 段落呼吸散掉 → 听感"不连贯"** |
| ② | **语调起伏平 34%** | 灵心 F0 起伏 CV 只有 **13.6%**，晓晓同句 **20.6%** |
| ③ | **短句句尾上扬** | 灵心「我没有解释。」句尾 **+61.9 Hz/s**，陈述句念成半句问；`tts.py` 无参数可修 |
| ④ | **逐句合成** | 31 个独立文件，每句自带句首/句尾静默，拼起来一顿一顿（这条是我自己的问题，跟 TTS 无关） |
| ⑤ | **句句在描述画面** | "她坐在火塘最外圈。只听。"——画面已经演了 |
| ⑥ | **句型全一样** | 10–16 字，全是完整主谓宾，没有长短交错 |

v5 对应处置：① 全片拉到 −26% / −28%（实测 3.1–3.4 字/秒），**且没有采用逐行 rate**——见下方说明 ②③ 换云健（句尾不扬）+ 晓晓（起伏 51%）④ 段落后合成、一句一句排进 245s 真实时间轴 ⑤ 只讲画面给不出的 ⑥ 8 字和 29 字混排。

**为什么没采用配音师的"逐行 rate"方案**：他反解出每行的理想 rate 跨度是 `−5% ~ −45%`，12/14 能落进 ±0.25s。但我这一版不需要把每句塞进固定时长——**我是先有 245s 的真实时间轴，再把句子按呼吸排进去**，所以不存在"不落位"的问题。而一行 −5%、下一行 −45%，等于让同一个人在 40 秒内变速两倍，那才是真的不像人。**一个解说员全程一个步速，靠句子长短和标点停顿做节奏**，这是我选的路。

**附带证据（配音师实测）**：edge-tts 的 `--rate` 调慢时，**内停顿总长同步变长**（0.97s → 1.66s）——"成段落"是慢下来的副产品，不是我调出来的。另外 `(1+rate) × 净语音 = 常数`（误差 <0.5%），所以真要精确控时长，一行试一次音就能解出 rate，不用试错。

## 五 · BGM《爱意》：解码为什么 Win 不行

**跟操作系统一点关系都没有。** 旧脚本在 Windows 上失败，是因为解码器本身算错了；mac 上那些工具（ncmdump 之类）之所以"能行"，是因为它用的是正确算法。

两个实现错误：

1. **密钥流算法用错了**。旧脚本用 RC4 的 KSA + PRGA 生成密钥流；ncmdump 实际用的是 **key_box 折叠算法**（对 256 字节表做 17 轮折叠，再按密钥流索引取值）。长得像 RC4，但不是。
2. **meta 少解一层**。meta 区必须 `meta[22:]` 先 **base64 解码**，再 AES-128-ECB 解密，再切掉前 6 字节 `music:` 前缀。旧脚本漏了 base64 那一步，解出来的东西当然对不上。

**AES 本身从来没问题**——用 NIST 标准测试向量自检是通过的。所以这不是"Windows 的加密库不一样"。

现在已解开：

| 项 | 值 |
|---|---|
| 容器 | `CTENFDAM`，key_len 128，核心密钥明文前缀 `neteasecloudmusic247`，box key 99 B |
| 音频 | **FLAC**，音频起点 offset 129243（解密后首 4 字节即 `fLaC`） |
| 参数 | 139.459501s / 44100 Hz / 2ch / 16bit / 762 kbps |
| 元数据 | `musicName=爱意(金风玉露变奏)`、`artist=陈致逸`、封面 128,398 B |
| 产物 | `.tmp/bgm/ai-yi.flac`（13.28 MB）、`ai-yi.wav`（48k/stereo/pcm_s16le，26.78 MB）、`ai-yi.meta.json` |
| 解码器 | `.tmp/audition/sd-decode-ncm.py`（幂等，可重跑） |

所以"win 不行"这个前提本身要撤掉——**Windows 现在能解，而且以后都能解**。

完整对位与 ducking 落点表见 `videos/zhi-guo-xiang/assets/bgm-ai-yi-map.md`（312 行，全部实测）。

| 第二遍 | 151.00–245.00 | **45.45754**–139.46（零交叉起播，避开 click） |

**没有照抄 spec 的压深表。** 那张表按旧稿（更密）的人声算；v5 的句子位置全变了，所以改成从人声轨**自动检测 36 个有声区间**，逐段实测 p90 反算压深。这一步顺带修掉一个真 bug：只遍历台词表的话，**诗六行和 D01 完全不会触发 ducking**，实测诗 L3 的余量只有 1.5 dB（等于被埋）。

**最终参数**

| 参数 | 值 | 为什么 |
|---|---|---|
| 基础增益 | **−11 dB** | 母版峰值 −0.35 dBFS，spec 建议 −8；实测 −8 时女独白 b01 只有 4.5 dB 余量，降到 −11 |
| ducking 判据 | `p90 ≥ −14` 触发 | spec §6.1 原公式 |
| 压深 | `clamp(round0.5(p90+17), 2.5, **9.0**)` | spec 上限 7.0，实测 a10 句尾「看了她一整夜」余量只剩 2.6 dB，放开到 9.0 |
| 包络 | −0.15s 起压 / +0.35s 放完，60ms 平滑 | 同 spec |
| 合并 | 间隔 <3s 并成一段 | 23 段 → **11 段**，避免"呼噜" |
| 女独白 | **+2 dB** | 晓晓母版比云健低 1.5 dB，抬回同一线 |
| 全人声 | **+1 dB** | 给句尾留余量 |
| 序段音乐 | 4–34s **+2 dB** | 该段人声余量 >10 dB，让音乐站出来 |

**体检结果：33 个有声段，最小余量 5.6 dB，没有一段低于 4 dB。**（唯一 5.6 的是 a10 句尾，云健自然收弱）
